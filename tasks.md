N=1 → ~1.580 ev/s, N=10 → ~5.340 ev/s (3,4x mais rápido), N=100 → ~7.170 ev/s, aproximando do teto de ~8.000 ev/s conforme N cresce. **Funciona e vale implementar** (pode ser a diferença entre 6s e 30s pra 50 mil elementos), mas não resolve entradas muito grandes — o resume da VM a cada linha via JDWP acontece de qualquer forma, mesmo sem emitir o evento
- [ ] Mitigação estrutural pra entradas *muito* grandes fica como ideia futura (não bloqueante): trocar JDI/JDWP por agente de bytecode (`java.lang.instrument` + ASM/ByteBuddy) sem round-trip de protocolo — não entra no MVP, só se o cap de escopo abaixo se mostrar insuficiente na prática
- [x] **Cap de eventos decidido: 5.000 eventos de step emitidos por execução.** Baseado nas taxas medidas (~360 ev/s com objetos complexos, ~1.580 ev/s com variáveis simples), isso mantém a execução instrumentada dentro de ~3-14s dependendo da complexidade do estado — janela aceitável de espera. Ao atingir o cap: para de emitir `step` (desabilita o `StepRequest`, deixa o programa rodar solto até terminar ou bater no timeout de execução) e emite `step_limit_exceeded`. Amostragem (N fixo, valor a calibrar na Fase 1) reduz a chance de bater nesse cap achatando o custo por evento; amostragem adaptativa/baseada em mudança de variável fica pra depois

## Decisão de ir/não ir (Fase 0.5) — **GO, com escopo explícito**

Segue pra Fase 1 com nsjail + JDI. O teto de ~8.000 eventos/s do protocolo JDWP é uma limitação física real, não um bug a corrigir — a decisão é tratar isso como **restrição de produto**, não como pendência técnica: o visualizador passo-a-passo é para entender a *mecânica* de um algoritmo em entradas pequenas/médias (como ferramentas comparáveis, ex. Python Tutor, já fazem por design), não para rodar entradas de tamanho realista de produção. A análise estática de Big-O (não o step-through) é o que informa sobre comportamento em escala.

Consequência direta pro design: a API e o frontend precisam comunicar esse limite explicitamente ao usuário (ex: "essa execução tem mais de N passos, mostrando os primeiros N" ou similar), em vez de deixar implícito ou deixar a execução travar num timeout sem explicação.

### Timeout de execução

- [ ] Definir o valor do `--time_limit` do nsjail (wall-clock único — modelo trace-and-replay não precisa de RLIMIT_CPU nem timeout de sessão separado, já que a sandbox nunca fica pausada esperando o usuário) — ainda usando os defaults de spike (`SPIKE_TIME_LIMIT`, 10s Java/15s C#, configurável via env var), não um valor de produção escolhido deliberadamente
- [x] **Emitir evento `timeout` com o trace parcial gerado até o momento em que a execução foi morta — implementado e validado de verdade nas duas linguagens.** `sandbox/src/events.rs::run_nsjail` (nova função compartilhada) troca o antigo `.status()` com stdio 100% herdado por `spawn()` + threads dedicadas de stdout/stderr: relay em tempo real pro nosso próprio stdout/stderr (preserva o comportamento anterior) enquanto vigia o stderr do nsjail por um marcador — e mata o processo se o output estourar um cap (ver `output_truncated` abaixo). Chamado a partir de `java::run()` e `csharp::run_outer()`.
  - **Achado real, não assumido**: nsjail devolve `128+sinal` como o próprio exit code do processo (`return 128 + WTERMSIG(status)` em `subproc.cc::reapProc`) tanto pra timeout quanto pra qualquer outro SIGKILL externo (ex: cgroup OOM) — os dois cenários são **literalmente o mesmo exit code (137)**, então exit code sozinho não distingue nada. A única diferença é uma linha de log `LOG_I` que o nsjail imprime só no caso de timeout: `pid=N run time >= time limit (T >= T) (...). Killing it`.
  - **Bug real encontrado e corrigido nesse processo**: `java.rs`/`csharp.rs` passavam `--quiet` pro nsjail, que suprime exatamente esse nível de log (`LOG_I`) — ou seja, o marcador de timeout nunca chegava no nosso stderr, e nenhum evento era emitido (silenciosamente cravado como `RunOutcome::Normal`). Corrigido removendo `--quiet` das duas invocações (comentado no código o porquê).
  - **Validado rodando de verdade dentro do Docker** (`docker run --privileged --cgroupns=host`, `sandbox-runner --language java|csharp` contra `InfiniteLoop.java`/`InfiniteLoop` C#, `SPIKE_TIME_LIMIT=6`): nsjail matou no segundo exato (`run time >= time limit (6 >= 6)`, `SIGKILL`, exit 137), e o stdout do processo mostrou `{"type":"timeout"}` como último evento em ambas as linguagens. C# mostrou a sequência completa esperada: 5.000 `step` (cap) + `step_limit_exceeded` + `timeout`.

- [x] **Capturar overflow de recursão como evento limpo (`stack_overflow`) — implementado e validado nas duas linguagens.** `RLIMIT_STACK` em si **não foi mexido** (mesma decisão já documentada na Fase 0.5: o runtime da linguagem falha limpo antes do SO precisar entrar, confirmado de novo aqui) — a detecção é via marcador de texto no stderr do processo, capturado pela mesma `events::run_nsjail`:
  - **Java**: `jdi/Debugger.java` já redireciona o stderr do processo-alvo pro seu próprio stderr (`redirectStream`), que por sua vez é capturado pelo `run_nsjail` do lado Rust. `java::run()` escaneia `stderr_lines` por `"StackOverflowError"`. Validado com `test-snippets/StackOverflowNoCatch.java` (recursão sem `try/catch`, sem base case) rodando de verdade: `Exception in thread "main" java.lang.StackOverflowError` no stderr → `{"type":"stack_overflow"}` no stdout, exit 0.

Corrigido igualando ao padrão do C#.
- [x] **Limitar tamanho/rate de output (stdout/stderr) com truncamento + evento `output_truncated` — implementado e validado nas duas linguagens.** `events::OUTPUT_BYTE_CAP = 10 MB` em `events.rs`: `run_nsjail` conta bytes relayed do stdout do processo jailed (que carrega TANTO o stdout do programa do usuário QUANTO os eventos JSON de step — não dá pra separar sem parsear cada linha primeiro) e mata o processo (`child.kill()`) assim que o cap é excedido, emitindo `{"type":"output_truncated"}` em seguida. Cap escolhido uma ordem de grandez acima do que uma execução legítima no cap de 5.000 steps produziria (poucos MB), especificamente pra não truncar trace legítimo. Validado com `test-snippets/OutputFlood.java` / `test-snippets-csharp/OutputFlood` (`println`/`Console.WriteLine` de uma string fixa de ~105 bytes em loop infinito): parou em exatamente ~10.485.8xx bytes (cap + 1 chunk de leitura) nas duas linguagens, `{"type":"output_truncated"}` como último evento.
- [ ] Truncar payload de variáveis grandes na serialização de eventos — já implementado desde a Fase 1 (profundidade/cap de array/campos em `Debugger.java::serializeValue`), não revisitado nesta tarefa; C# não tem essa cobertura ainda (locals são só primitivo/string/array, sem objetos genéricos)
- [x] **Emitir evento `memory_limit_exceeded` quando o cgroup matar a execução por OOM — implementado e validado, com um gap real e documentado no lado C#.**
  - **Mecanismo 1 (as duas linguagens): SIGKILL do processo que o nsjail lançou diretamente.** `events::run_nsjail` classifica um SIGKILL sem o marcador de timeout (ver acima) como `RunOutcome::LikelyOom` — inferência por eliminação: nesta configuração de sandbox, `cgroup_mem_max` é o único outro mecanismo capaz de entregar um SIGKILL não anunciado (confirmado lendo o source do nsjail: `cgroup2.cc`/`subproc.cc` não logam nada específico de OOM, o kernel mata direto). **Achado importante**: `cgroup_mem_max` **não** é reforçado de verdade neste ambiente de dev (Docker Desktop/macOS, VM Linux aninhada) — mesma limitação já documentada na Fase 0.5/1 (precisa de Linux real, ex. VM Lima, pra validar o cgroup como fronteira confiável). Por isso a validação aqui foi por **proxy**: `kill -9` direto no processo (mesmo mecanismo de entrega de sinal que um OOM kill real usaria), não um OOM de cgroup genuíno. Validado assim pras duas linguagens: matar o filho direto do nsjail (JVM `Debugger`, ou `sandbox-runner --csharp-worker`) produz `{"type":"memory_limit_exceeded"}`.
  - **Mecanismo 2 (achado específico do Java, corrigido): a arquitetura de 2 processos do JDI escondia o problema.** `LaunchingConnector` roda o alvo como uma JVM **separada** da JVM `Debugger` — um OOM kill real do cgroup mataria o alvo (quem de fato segura a memória), não o `Debugger` (filho direto do nsjail que o mecanismo 1 observa). Confirmado empiricamente: matar a JVM alvo diretamente faz o `Debugger` só ver um `VMDeathEvent` normal e sair com status 0 — **silenciosamente engolindo a falha**. Corrigido em `jdi/Debugger.java`: depois do loop de eventos, checa `vm.process().exitValue()`; se `== 137` (convenção `128+SIGKILL`), emite `{"type":"memory_limit_exceeded"}` antes de sair. Validado via `kill -9` no processo-alvo (proxy) **e** organicamente: rodando `OutputFlood.java` (que também gera pressão de memória via GC/alocação de String) o alvo foi morto com SIGKILL de verdade e o evento saiu correto sem intervenção manual.
  - **Gap real, documentado como limitação honesta (não corrigido): o mesmo problema existe no C#, sem solução limpa encontrada.** `run_worker()` também lança o alvo (`dotnet <dll>`) como processo OS separado via `CreateProcessForLaunch`. Tentei a mesma correção do Java — reaping manual via `waitpid(pid, ..., WNOHANG)` bruto (FFI, sem crate `libc`) — mas testado de verdade (matando o processo `dotnet` alvo diretamente, mesma técnica de proxy): o callback `ExitProcess` do ICorDebug **nunca dispara** pra um alvo morto externamente via SIGKILL (esperado o deadline interno inteiro de 15s, confirmado via log, não é só uma corrida de reap) — então nem chega a tentar o `waitpid`. Não achei nenhum slot de vtable do `ICorDebug` (dos já implementados, nem pesquisando mais) que exponha o exit status bruto do alvo depois disso. **Consequência**: `memory_limit_exceeded` em C# só dispara hoje quando o OOM mata o `run_worker` em si (mecanismo 1); um OOM que mate especificamente o processo `dotnet` alvo cai como uma falha genérica não-explicada, igual comportamento de antes desta tarefa.
