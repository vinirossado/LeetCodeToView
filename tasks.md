Qualquer algoritmo com mais de algumas dezenas de milhares de elementos **não termina de rodar dentro de um timeout de execução razoável** sob instrumentação passo a passo. - [x] **3 experimentos controlados pra achar a causa raiz** (toggle via env vars `SPIKE_SUSPEND`/`SPIKE_SKIPDATA` no driver): (A) `SUSPEND_ALL` + extração completa = ~1.584 ev/s; (B) `SUSPEND_EVENT_THREAD` + extração completa = ~1.577 ev/s (suspend policy não faz diferença, só 1 thread no alvo); (C) `SUSPEND_ALL` sem extrair locals/stack = ~7.959 ev/s (extração é ~80% do custo, mas o teto de ~8.000 ev/s mesmo sem extrair nada mostra que **o gargalo real é o round-trip síncrono do protocolo JDWP em si**, não a extração de dados nem a suspend policy)
- [x] **Cold start medido com precisão (5 execuções, `test-snippets/Trivial.java`)**: ~470ms médios (458-485ms) pro pipeline completo. Comparado com JVM sozinha sem JDI no mesmo container (~18ms) — **a causa não é o boot da JVM, é o handshake do `LaunchingConnector`/JDWP** (2ª JVM em modo debug + conexão do debugger). Corrige a suposição anterior no `spec.md` de que seria "cold start de JVM" genérico — muda a mitigação: warm pool de JVMs simples não resolve, porque o custo é abrir uma sessão de debug nova a cada execução, não o boot em si
- [x] **Amostragem de step prototipada e testada** (flag `-Dspike.sample=N` no driver: extrai/emite dados só a cada N eventos, resume sem extrair nos outros). N=1 → ~1.580 ev/s, N=10 → ~5.340 ev/s (3,4x mais rápido), N=100 → ~7.170 ev/s, aproximando do teto de ~8.000 ev/s conforme N cresce. **Funciona e vale implementar** (pode ser a diferença entre 6s e 30s pra 50 mil elementos), mas não resolve entradas muito grandes — o resume da VM a cada linha via JDWP acontece de qualquer forma, mesmo sem emitir o evento
- [ ] Mitigação estrutural pra entradas *muito* grandes fica como ideia futura (não bloqueante): trocar JDI/JDWP por agente de bytecode (`java.lang.instrument` + ASM/ByteBuddy) sem round-trip de protocolo — não entra no MVP, só se o cap de escopo abaixo se mostrar insuficiente na prática
- [x] **Cap de eventos decidido: 5.000 eventos de step emitidos por execução.** Baseado nas taxas medidas (~360 ev/s com objetos complexos, ~1.580 ev/s com variáveis simples), isso mantém a execução instrumentada dentro de ~3-14s dependendo da complexidade do estado — janela aceitável de espera. Ao atingir o cap: para de emitir `step` (desabilita o `StepRequest`, deixa o programa rodar solto até terminar ou bater no timeout de execução) e emite `step_limit_exceeded`. Amostragem (N fixo, valor a calibrar na Fase 1) reduz a chance de bater nesse cap achatando o custo por evento; amostragem adaptativa/baseada em mudança de variável fica pra depois

## Decisão de ir/não ir (Fase 0.5) — **GO, com escopo explícito**

Segue pra Fase 1 com nsjail + JDI. O teto de ~8.000 eventos/s do protocolo JDWP é uma limitação física real, não um bug a corrigir — a decisão é tratar isso como **restrição de produto**, não como pendência técnica: o visualizador passo-a-passo é para entender a *mecânica* de um algoritmo em entradas pequenas/médias (como ferramentas comparáveis, ex. Python Tutor, já fazem por design), não para rodar entradas de tamanho realista de produção. A análise estática de Big-O (não o step-through) é o que informa sobre comportamento em escala.

Consequência direta pro design: a API e o frontend precisam comunicar esse limite explicitamente ao usuário (ex: "essa execução tem mais de N passos, mostrando os primeiros N" ou similar), em vez de deixar implícito ou deixar a execução travar num timeout sem explicação.

- [x] **Emitir evento `memory_limit_exceeded` quando o cgroup matar a execução por OOM — implementado e validado, com um gap real e documentado no lado C#.**
  - **Mecanismo 1 (as duas linguagens): SIGKILL do processo que o nsjail lançou diretamente.** `events::run_nsjail` classifica um SIGKILL sem o marcador de timeout (ver acima) como `RunOutcome::LikelyOom` — inferência por eliminação: nesta configuração de sandbox, `cgroup_mem_max` é o único outro mecanismo capaz de entregar um SIGKILL não anunciado (confirmado lendo o source do nsjail: `cgroup2.cc`/`subproc.cc` não logam nada específico de OOM, o kernel mata direto). **Achado importante**: `cgroup_mem_max` **não** é reforçado de verdade neste ambiente de dev (Docker Desktop/macOS, VM Linux aninhada) — mesma limitação já documentada na Fase 0.5/1 (precisa de Linux real, ex. Por isso a validação aqui foi por **proxy**: `kill -9` direto no processo (mesmo mecanismo de entrega de sinal que um OOM kill real usaria), não um OOM de cgroup genuíno. Validado assim pras duas linguagens: matar o filho direto do nsjail (JVM `Debugger`, ou `sandbox-runner --csharp-worker`) produz `{"type":"memory_limit_exceeded"}`.

Corrigido em `jdi/Debugger.java`: depois do loop de eventos, checa `vm.process().exitValue()`; se `== 137` (convenção `128+SIGKILL`), emite `{"type":"memory_limit_exceeded"}` antes de sair. Validado via `kill -9` no processo-alvo (proxy) **e** organicamente: rodando `OutputFlood.java` (que também gera pressão de memória via GC/alocação de String) o alvo foi morto com SIGKILL de verdade e o evento saiu correto sem intervenção manual.

Dado que esse é exatamente o caso mais comum pra uma ferramenta de aprendizado por step-through (usuário escreve um bug de propósito), esse é um bug de correção central, não um detalhe de hardening.
  - **3 causas raiz distintas, todas corrigidas em `jdi/Debugger.java`**:
    1. **Falta o check em si**: adicionado `else if (exitValue != 0)` ao lado do `== 137` já existente — captura QUALQUER saída anormal do alvo, não só SIGKILL.
    2. **Race real na checagem de `exitValue`, achado ao debugar por que o novo check nunca disparava**: `vm.process().exitValue()` chamado logo após o loop de eventos (mesmo ponto onde o mecanismo 2 do `memory_limit_exceeded` já lia) lançava `IllegalThreadStateException` (silenciosamente engolida pelo catch existente) — `VMDeathEvent` disparar NÃO garante que o processo do SO já foi coletado (`reaped`) pelo lado Java; uma saída por exceção faz mais trabalho antes de sair de verdade (stack trace, possíveis shutdown hooks) que um SIGKILL cru, expondo a corrida onde o SIGKILL aparentemente não. Confirmado com um `System.err.println` de debug temporário que simplesmente nunca rodava. Corrigido com `vm.process().waitFor(5, TimeUnit.SECONDS)` antes de ler `exitValue()`. **Acender uma dúvida honesta pro mecanismo 2 pré-existente do `memory_limit_exceeded`**: como esse MESMO ponto de código sofria dessa corrida, é possível que aquele caminho (137) também dependesse de sorte de timing em alguns runs — não investigado a fundo aqui (fora do escopo desta correção), mas o `waitFor` adicionado agora protege os dois casos igualmente.

Um TAB cru dentro de uma string JSON é **inválido pela RFC 8259** — o parser da API (`Jackson ObjectMapper.readTree` em `ExecutionJob.parseEventOrStdout`) rejeitava a linha inteira, que caía no fallback de "não é JSON válido" e virava um evento `stdout` comum em vez de `error` — confirmado via `POST /executions` real (o evento aparecia como texto bruto dentro de um `{"type":"stdout",...}`, com a mensagem genérica sanitizada aparecendo LOGO DEPOIS, já que o último evento real não era `error`). Corrigido generalizando `escapeJson` pra escapar TODOS os caracteres de controle (`< 0x20`), não só os dois com escape curto do JSON — **acha um bug latente mais amplo de graça**: os outros 4 call sites de `escapeJson` (serialização de `String`/`char` de variáveis do programa do usuário) tinham o mesmo problema — uma `String` do usuário contendo um TAB (ou qualquer controle) já corromperia o evento `step` inteiro daquele passo, silenciosamente, antes desta correção.
