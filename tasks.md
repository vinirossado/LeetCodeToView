## Fase 2+ — UX/acessibilidade pós-MVP

- [ ] **`frontend/src/app/features/editor/code-editor.component.ts` importa um módulo INTERNO do `monaco-editor` (`esm/vs/editor/browser/config/tabFocus.js`, ver o doc comment do import `TabFocus` nesse arquivo) em vez do caminho documentado (`editor.action.toggleTabFocusMode` via `editor.trigger`/o atalho real Ctrl+M).** Achado real, não teórico: numa build de produção real desta app (Angular esbuild), nem `editor.trigger(...)` nem o atalho de teclado REAL Ctrl+M/Ctrl+Shift+M de fato mudavam o `tabFocusMode` — confirmado com um teste ponta-a-ponta apertando o atalho de verdade num editor focado e checando que Tab continuava preso (`e2e/tests/keyboard-accessibility.spec.ts`'s investigação, não o teste final que ficou). Ler `TabFocus.getTabFocusMode()`/`setTabFocusMode()` direto do singleton interno resolveu (é o mesmo módulo que `editorConfiguration.js` já lia por baixo dos panos) e está validado — mas é um import sem contrato público, sem `.d.ts` oficial (tipagem própria em `frontend/src/types/monaco-internal.d.ts`), então um upgrade futuro do `monaco-editor` (hoje pinado em `^0.52.2`) pode mover/renomear esse arquivo silenciosamente sem quebrar o build (TS só reclamaria se o caminho do módulo mudasse; se só o *comportamento* do singleton mudar, quebra silenciosa). Gatilho de revisão: qualquer bump de `monaco-editor` no `package.json` — rodar `e2e/tests/keyboard-accessibility.spec.ts` de novo antes de dar merge.

## Fase 1 — MVP com Java + C#

- [ ] **Travamento do stepper do ICorDebug em `StartCore` (`Thread.Start()`) — agora com causa raiz LOCALIZADA via símbolos de debug reais do CoreCLR (não mais "sem símbolos, não dá pra saber"), mas CONFIRMADO como deadlock genuíno de dentro do próprio CoreCLR, sem fix seguro do lado do driver.** Terceira rodada de investigação: os símbolos de debug reais da Microsoft pro `libcoreclr.so` desta build exata (.NET SDK 8.0.424 / runtime `Microsoft.NETCore.App` 8.0.30, linux-arm64, BuildID `731505cd1869cd17135512122db47edb662339ca`) **existem e são baixáveis** — `dotnet tool install -g dotnet-symbol` (pacote oficial `dotnet/symstore`), depois `dotnet-symbol --symbols --modules -o <dir> <path-para-libcoreclr.so>` baixa um `libcoreclr.so.dbg` de ~40MB do servidor público `https://msdl.microsoft.com/download/symbols/` (a flag `--debugging` sozinha NÃO traz os símbolos — só DAC/DBI/SOS; é `--symbols` que traz o `.dbg` de verdade). Colocado em `/usr/lib/debug/.build-id/73/1505cd...debug` (convenção padrão de build-id do `gdb`), `gdb -p <pid>` passou a resolver TODOS os frames com nome de função real (confirmado: 26955 símbolos, incluindo `ThreadNative_Start`, `WatsonLastChance`, `NotifyDebuggerLastChance` batendo com o que a leitura de código da rodada anterior já sugeria). Reproduzido de novo (`MultiThreadCs`, `sandbox-runner --csharp-worker --dll <path>` direto sem nsjail, com o guard de multi-thread do `com.rs` temporariamente elevado só pro diagnóstico — nunca mergeado — já que o guard de produção bloqueia ANTES da corrida acontecer). Backtrace resolvido real: a thread principal está legitimamente em `Thread::JoinEx` (o próprio `t.Join()` do programa); as threads de trabalho estão todas travadas competindo pelo MESMO `AwareLock` (o lock interno de sincronização do `Console.WriteLine`) via `AwareLock::Enter`/`JIT_MonEnter_Helper`; e pelo menos uma delas está presa exatamente em `Debugger::DetachThread` (`debugger.cpp:9074`, chamada durante o cleanup de término de uma thread gerenciada, `Thread::OnThreadTerminate` → `ThreadNative::KickOffThread`) → `Thread::RareDisablePreemptiveGC` → `Thread::WaitSuspendEvents` → `CLREventBase::WaitEx`, esperando um evento de liberação de suspensão que nunca chega — enquanto ISSO seguraria o `AwareLock`, travando todas as outras. **Descartado**: não é o mesmo bug do travamento em exceção C# não tratada, já corrigido (ver `git log` — fix de `ICorDebugManagedCallback2`/`QueryInterface` em `com.rs`, mais dois gaps de seccomp/exit-code achados na sequência) — rodado de novo com esse fix já aplicado, este item aqui continua travando 15/15 execuções, idêntico em mecanismo. **Achado extra, forte evidência de que é upstream genuíno, não algo que o driver controla**: essa MESMA família de deadlock (`Thread::RareDisablePreemptiveGC` → `Thread::WaitSuspendEventsHelper` → `CLREventBase::Wait`, brigando com o lock do `DebuggerController`/notificação do debugger) é um bug real, ATUALMENTE ABERTO, reconhecido pela própria Microsoft — dotnet/runtime#126096 ("Debugger hangs due to runtime deadlock", aberto 2026-03-25, reabertura de dotnet/runtime#123650 depois que o fix em #123651 não resolveu de vez), com "Known Workarounds: None known" no próprio relato oficial. Caminho exato não é idêntico ao nosso (o deles envolve lookup de info R2R + lock do `DebuggerController` durante exceção nativa; o nosso envolve `Debugger::DetachThread` durante criação/término de múltiplas threads), mas é a MESMA classe de corrida na MESMA sub-rotina de suspensão do CoreCLR — corrobora que não há workaround seguro conhecido nem pela própria Microsoft. **Conclusão**: investigado ao limite prático disponível — símbolos resolvidos, função exata identificada, cross-referenciado com um bug upstream real e aberto na mesma sub-rotina. Não é mais uma hipótese "não dá pra saber sem símbolos": os símbolos foram obtidos, resolveram o backtrace completo, e o resultado é um deadlock genuíno dentro do próprio `libcoreclr.so` (bookkeeping de suspend-all/GC-mode-transition), não algo que `com.rs` causa ou pode evitar (o driver já chama `Continue()` corretamente em todo callback que recebe — a thread presa nunca chega a gerar um callback pro driver reagir). Única opção restante não tentada: compilar o CoreCLR em Debug a partir do source pra rastrear a condição de corrida exata linha a linha — descartado por ora como desproporcional (Microsoft já reconhece o bug e não tem workaround). **Nota de metodologia pra quem retomar**: mesma reprodução direta (`sandbox-runner --csharp-worker --dll <path>`, sem nsjail) da rodada anterior, mais os símbolos via `dotnet-symbol` (funciona de verdade, confirmado — usar `--symbols`, não só `--debugging`).
